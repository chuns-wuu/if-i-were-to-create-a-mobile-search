Context

What I'd build

The mobile CRM lets field reps look up anyone tied to a patient program from a phone: patients, their caregivers, prescribers (HCPs), clinics and hospitals (HCOs), provider office staff, and program-level contacts. Before this work each entity had its own store and its own query shape. The unified API turns them into one ranked, paginated, permission-checked, HIPAA-masked search, plus a profile view and a paginated "linked contacts" view.

GraphQL resolver→ validate + sanitize→ authorize per type→ name CTE per entity→ match + rank→ page→ attach links→ mask + convert

Search, profile, and linked-contacts queries ship from one Lambda: lookupContacts, contactDetails, and contactAssociations. Two frontend engineers, Aaron Brooks and Jason Goh, built the mobile UI on top of the API at the same time, so the contract had to stay usable while it was still changing.

How the work reads

01 · Engineering

Backend depth across entities

Strong evidence
Outcomes
  • One API for every contact type. The mobile app calls one search, one profile, and one linked-contacts query instead of a different query per entity.
  • New types plug in cheaply. Adding a contact type means adding one CTE. Matching, ranking, and paging stay the same.
  • Access rules extend without rewrites. A teammate later layered provider-level access restrictions (HC-101) onto the guard without touching the query.
Actions

The hard part was shape, not volume. Providers and HCOs live in relational tables, patients live in a JSONB cache, and caregivers are rows inside an address-book array on the patient.

  • Normalized every data shape. One CTE per entity emits the same columns (id, name, last name, external id, type), then matching, ranking, paging, and link expansion run once over the union.
  • Gave caregivers a stable identity. Caregivers have no ID of their own, so you built a composite key (patientId:contactBookId) with the delimiter in a shared constant that the SQL split calls and the TypeScript converter both use, so the two can't drift apart.
  • Modelled links as explicit pairs. Every link between types (for example HCP→patient, patient→caregiver) is typed. Where the database has no HCO→HCP link, the code reads the HCP→HCO link backwards and says so in a comment.
  • Authorized before querying. A separate ContactAccessGuard turns a user's role into allowed types and allowed links before any SQL runs, and the query is built only from what is allowed.

02 · Product instinct and execution

Iterating on requirements as they arrived

Strong evidence
Outcomes
  • Search results reps can trust. Exact matches and primary links rise to the top, and hidden patients never sort by a fake value.
  • The mobile client never broke. Every contract change shipped backward compatible while the UI was being built on it.
  • Cleaner, more relevant results. Archived providers no longer leak into search, and previews show what reps actually need.
Actions

Requirements kept changing as the mobile UI came together, and the history shows a steady loop: ship, see it in the app, tighten. The ranking is the clearest example. It started as plain matching and ended as a documented, ordered set of rules.

  • Refined ranking with real use. Case-insensitive order (PR-02), then exact matches first, then last name when one exists (MOB-119), then primary links first (MOB-120). Masked names sort as empty and fall back to external ID.
  • Widened the search scope. Added search by external ID (MOB-121), showed the external ID as the preview subtitle (MOB-110), and dropped addresses from previews (MOB-122).
  • Kept the contract clean. Trimmed the GraphQL schema (MOB-123), replaced hasNext with the shared Page interface (MOB-102), and retired LegacyContactKind in stages with a "to be deprecated" marker (MOB-124).
  • Fixed data correctness. Stopped archived providers leaking into results (MOB-112), sped up JSONB archive checks (MOB-125), and added an isPrimary flag on associations.

03 · Simplification

One source of truth for HIPAA masking

Strong evidence
Outcomes
  • One source of truth. Backend and frontend import the same mask constants, so there are no local copies to drift.
  • Hidden is never confused with empty. The sentinels can't collide with real data, so the UI reliably detects a masked value.
  • Teammates built on it right away. Masked phone and email can't start a call or message (MOB-111), masked values are hidden from contact dropdowns (MSG-101), and the patient profile switched to the shared constants (PR-03).
Actions

Patients without HIPAA consent must show masked values. At first the backend used its own ASCII strings (******, ***-***-****) inside the converter, and the web app kept its own mask literals. A real value could collide with the mask, and the UI had no reliable way to tell "hidden" from "empty".

  • Masked at the source. Columns are tagged MaskedColumn, so the masked value is produced once, in the query, and paging, sorting, and links all see the same value.
  • Centralized the masks. The masks moved into @medlink/constants/obfuscation, imported by backend and frontend alike.
  • Designed collision-proof sentinels. Each mask uses heavy asterisks plus a zero-width space, so no real data can equal it and the UI can detect a masked value with a plain set lookup.
  • Removed duplicate masking code. Deleted the converter's local mask strings and the masking logic in the result processor (MOB-106).

04 · Verification

Tests, end-to-end coverage, and load

Partly verifiable
Outcomes
  • Rules checked against a real database. Every permission and masking rule runs against a Postgres test database, not mocks.
  • Mobile flows covered end to end. The mobile Playwright suite exercises the API through real contact flows.
  • Latency visible per request. Search time shows up in CloudWatch at both the DAO and resolver layers.
Actions

Automated testing is the strongest part of this dimension. Every major PR shipped with its tests, and more test code than production code overall.

  • Built a realistic tenant fixture. One shared fixture models every contact type, patients with and without consent, and archived records, so each permission and masking rule is checked against realistic data.
  • Covered the mobile flows end to end. The Playwright suite runs patient profile, patient associations, HCO profile, HCP profile, and creating email and SMS from a contact through your API. Teammates wrote those specs. Your own Playwright work is on a later feature (PR-04, PR-05).
  • Instrumented latency. Search time is logged at the DAO and resolver layers (Timer in MOB-114).

05 · Planning

Shipping in thin, safe slices

Strong evidence
Outcomes
  • The UI never waited on the backend. Each layer landed before the screen that needed it.
  • Reviews stayed small. Large items were split into "Part 1" PRs that could be reviewed quickly.
  • A stable stack. Nothing on the search stack had to be reverted, while the mobile comms area had reverts elsewhere in the same period.
Actions
  • Built bottom-up. Data access with tests first, then the API, then pagination, then permissions, then masking, then profiles, so every step was mergeable on its own.
  • Split large items. "Part 1" PRs for MOB-129 and MOB-110 kept each review focused.
  • Shipped in short, steady increments. Core PRs followed each other closely, starting with the API the day after the data layer.

Challenges

Problems a new hire had to solve

New codebase, healthcare rules

Problem

A multi-tenant monorepo with per-customer Postgres schemas, DynamoDB, and HIPAA access tiers, learned while the project was starting.

Response

Started with smaller fixes and refactors to learn the platform, then took ownership of the backend for a new product area.

Many data shapes, one result list

Problem

Relational rows, JSONB documents, and nested arrays had to rank and page together.

Response

Per-entity CTEs that emit one common row shape, with a composite key for caregivers who had no ID.

Permissions before data

Problem

Each role sees a different set of types and links. Filtering after the query would leak counts and break paging.

Response

The authorizer decides allowed types and links first, and the SQL is built only from what is allowed.

Masking that stays consistent

Problem

Mask strings defined twice, collision with real data, and sort order based on hidden values.

Response

Masking in SQL, shared sentinel constants, and masked values sorted as empty with an external-ID fallback.

A contract under active use

Problem

Two frontend engineers built on the API while it was still changing.

Response

Staged deprecations, the shared Page interface, and pairing with Jason on the profile endpoint.

Free-text input into SQL

Problem

Search text feeds Postgres regex matching, so special characters could break queries.

Response

Escaping of Postgres and regex reserved characters, trimming, and plain-language errors that Aaron's UI shows to reps.
