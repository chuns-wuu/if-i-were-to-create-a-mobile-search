Context

What was built, and for whom

The mobile CRM lets field reps look up anyone tied to a patient program from a phone: patients, their caregivers, prescribers (HCPs), clinics and hospitals (HCOs), provider office staff, and program-level contacts. Before this work each entity had its own store and its own query shape. The unified API turns them into one ranked, paginated, permission-checked, HIPAA-masked search, plus a profile view and a paginated "linked contacts" view.

GraphQL resolver→ validate + sanitize→ authorize per type→ name CTE per entity→ match + rank→ page→ attach links→ mask + convert

Three GraphQL queries ship from one Lambda: searchContacts, contactProfile, and contactRelations. Two frontend engineers, Aaron Brooks and Jason Goh, built the mobile UI on top of the API at the same time, so the contract had to stay usable while it was still changing.

The hard part was shape, not volume. Providers and HCOs live in relational tables. Patients live in a JSONB cache. Caregivers are rows inside an address-book array on the patient. You normalized all of them with one CTE per entity that emits the same columns (id, name, last name, external id, type), then ran matching, ranking, paging, and link expansion once over the union.

  • Caregivers have no ID of their own, so you built a composite key (patientId:contactBookId) and moved the delimiter into a shared constant that the SQL split calls and the TypeScript converter both use.
  • Links are modelled as 14 explicit pairs (for example HCP→patient, patient→caregiver). Where the database has no HCO→HCP link, the code reads the HCP→HCO link backwards and says so in a comment.
  • Authorization is a separate ContactAccessGuard. It turns a user's role into allowed types and allowed links before any SQL runs. A teammate later layered provider-level global access restrictions (HC-101) onto this structure in a couple hundred lines.

Requirements kept changing as the mobile UI came together, and the history shows a steady loop: ship, see it in the app, tighten. The ranking is the clearest example. It started as plain matching and ended as a documented three-step order.

  • Ranking. Case-insensitive order (PR-02), then exact matches first, then last name when one exists (MOB-119), then primary links first (MOB-120). Masked names sort as empty and fall back to external ID, so hidden patients never sort by a fake value.
  • Search scope. Added search by external ID (MOB-121). Showed the external ID as the preview subtitle (MOB-110) and dropped addresses from previews (MOB-122).
  • Contract hygiene. Trimmed the GraphQL schema (MOB-123), replaced hasNext with the shared Page interface (MOB-102), and retired LegacyContactKind in stages, leaving a "to be deprecated" marker so the mobile client never broke (MOB-124).
  • Data correctness. Archived providers leaking into results (MOB-112), faster JSONB archive checks (MOB-125), and an isPrimary flag on associations.

One source of truth for HIPAA masking

Strong evidence

3

Patients without HIPAA consent must show masked values. At first the backend used its own ASCII strings (******, ***-***-****) inside the converter, and the web app kept its own mask literals. A real value could collide with the mask, and the UI had no reliable way to tell "hidden" from "empty".

  • Masking moved into the query: columns are tagged MaskedColumn, so the masked value is produced once, at the source, and paging, sorting, and links all see the same value.
  • The masks moved into @medlink/constants/obfuscation, imported by backend and frontend alike. Each one uses heavy asterisks plus a zero-width space, so no real data can equal it and the UI can detect a masked value with a plain set lookup.
  • Teammates built on it right away: masked phone and email can't start a call or message (Jason, MOB-111), masked values are hidden from contact dropdowns (MSG-101), and the patient profile switched to the shared constants (PR-03).

Challenges

Problems a new hire had to solve

New codebase, healthcare rules

Problem

A multi-tenant monorepo with per-customer Postgres schemas, DynamoDB, and HIPAA access tiers, learned while the project was starting.

Response

Spent eight weeks on smaller fixes and refactors, then took the backend for a new product area. Roughly 90% of its lines are still yours today.

Six data shapes, one result list

Problem

Relational rows, JSONB documents, and nested arrays had to rank and page together.

Response

Per-entity CTEs that emit one common row shape, with a composite key for caregivers who had no ID.

Permissions before data

Problem

Each role sees a different set of types and links. Filtering after the query would leak counts and break paging.

Response

The authorizer decides allowed types and links first, and the SQL is built only from what is allowed.

Masking that stays consistent

Problem

Mask strings defined twice, collision with real data, and sort order based on hidden values.

Response

Masking in SQL, shared sentinel constants, and masked values sorted as empty with an external-ID fallback.

A contract under active use

Problem

Two frontend engineers built on the API while it was still changing.

Response

Staged deprecations, the shared Page interface, and pairing with Jason on the profile endpoint.

Free-text input into SQL

Problem

Search text feeds Postgres regex matching, so special characters could break queries.

Response

Escaping of Postgres and regex reserved characters, trimming, and plain-language errors that Aaron's UI shows to reps.
