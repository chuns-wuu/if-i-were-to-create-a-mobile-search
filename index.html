If I were to build a unified contact search for a mobile CRM

A healthcare company is launching a new mobile app for field reps. They need one backend to search and view everyone tied to a patient program. Here is the requirement as I would receive it, and how I would design, build, test, and ship it.

The requirement

What the product needs

Field reps need to look up anyone tied to a patient program from a phone: patients, their caregivers, prescribers (HCPs), clinics and hospitals (HCOs), provider office staff, and program-level contacts. Today each type has its own store and its own query shape. The mobile team wants one search box, a profile screen, and a list of linked contacts.

R1 · SEARCH

One ranked search

One search box over all six types, ranked sensibly, with paging for infinite scroll.

R2 · PROFILE

Profile and links

A profile per contact, plus a paginated list of linked contacts (a patient's caregivers, an HCP's patients, and so on).

R3 · ACCESS

Role-based visibility

Each role sees only some types and links. Hidden records must not leak through counts or paging.

R4 · HIPAA

Masking without consent

Patients without HIPAA consent show masked values, and the app must not call, text, or email a masked value.

R5 · DATA

Mixed data shapes

Providers and HCOs are relational rows. Patients are a JSONB cache. Caregivers are rows inside an array on the patient, with no ID of their own.

R6 · TEAM

Parallel UI build

Two frontend engineers build the app at the same time, so the API contract will change while it is in use.

Proposed solution

One pipeline, run once over every type

GraphQL resolver→ validate + sanitize→ authorize per type→ name CTE per entity→ match + rank→ page→ attach links→ mask + convert

I would ship three GraphQL queries from one Lambda: searchContacts, contactProfile, and contactRelations. Each entity gets its own small CTE that turns its native shape into one common row. Matching, ranking, paging, and link expansion are then written once over the union, not six times. Authorization runs before the SQL is built, and masking happens inside the query, so every later step sees the same values.

Design decisions

How I would handle each part

Each panel pairs the requirement with the approach. The pill names the main risk that part of the design is meant to remove.

01 · Engineering

One query over six data shapes

Risk · six code paths
Requirement
  • 6 contact types in relational rows, JSONB, and nested arrays (R5)
  • ~14 link pairs between types (R2)
  • Different allowed types and links per role (R3)
How I'd solve it

The hard part is shape, not volume. I would write one CTE per entity that emits the same columns: id, display name, last name, external id, and type. Everything after that runs once over the union.

  • Caregivers without IDs. Build a composite key (patientId:contactBookId). Keep the delimiter in one shared constant, used by both the SQL split and the TypeScript converter, so the two can never drift apart.
  • Links as explicit pairs. Model the ~14 links as a typed list (HCP→patient, patient→caregiver, and so on). Where the database only stores one direction, such as HCP→HCO, read it backwards for HCO→HCP and document that in code.
  • Authorization first. A separate ContactAccessGuard turns the user's role into allowed types and allowed links before any SQL is built. Later rules, such as provider-level access limits, plug into the guard without touching the query.
Covers R2 · R3 · R5
02 · Product instinct and execution

Plan for the requirements to move

Risk · contract churn
Requirement
  • "Sensible" ranking, which will be defined by using the app (R1)
  • A contract that two engineers build on while it changes (R6)
  • Likely follow-ups: search by external ID, preview subtitle, hiding archived records
How I'd solve it

Requirements will change once the UI is in reps' hands. The design should make the expected changes cheap: ship, watch it in the app, tighten.

  • Ranking as a documented, ordered list. Start with case-insensitive matching, then add exact matches first, last name when one exists, and primary links first. Masked names sort as empty and fall back to external ID, so hidden patients never sort by a fake value.
  • Matching in one place. Because matching is written once over the union, adding search by external ID or changing the preview subtitle is a one-file change.
  • Contract hygiene from day one. Use a shared Page interface for every list instead of ad hoc hasNext flags. Keep changes additive, and retire old fields in stages with a "to be deprecated" marker so the mobile client never breaks.
  • Data correctness. Filter archived records in the CTEs, use fast JSONB checks for the archive flag, and expose isPrimary on associations so the UI can badge them.
Covers R1 · R6
03 · Simplification

Mask once, at the source

Risk · PHI exposure
Requirement
  • Mask patients without HIPAA consent (R4)
  • The app must tell "hidden" apart from "empty"
  • No call, text, or email to a masked value
How I'd solve it

The common failure is masking twice: the backend writes its own ASCII masks (******, ***-***-****) in a converter, and the frontend keeps its own copies. Real data can collide with the mask, and the UI can't reliably tell a hidden value from an empty one. I would avoid that from the start.

  • Mask in the query. Tag sensitive columns as MaskedColumn, so the masked value is produced once, in SQL. Paging, sorting, and links then all see the same value.
  • One shared constants module. Put the masks in @app/constants/obfuscation and import it from both backend and frontend. No local copies.
  • Sentinels that can't collide. Build each mask from heavy asterisks plus a zero-width space, so no real value can equal it. The UI detects a masked value with a plain set lookup and disables call, SMS, and email for it.
Covers R4
04 · Verification

Tests, end-to-end coverage, and load

Risk · silent regressions
Requirement
  • Permission and masking rules that must never regress (R3, R4)
  • A phone app where slow search is immediately visible (R1)
  • Two UI engineers depending on stable behavior (R6)
How I'd solve it

Every slice ships with more test lines than code, aiming for about 2 test lines per production line. Tests run against a real Postgres test database, not mocks.

  • Realistic fixture. One shared fixture models a full tenant: every contact type, patients with and without consent, archived records, and primary and non-primary links.
  • Permission matrix. Table-driven tests over role × contact type × link, checking both results and counts, so nothing leaks through paging.
  • End-to-end. Playwright flows for the mobile app: search, patient profile, linked contacts, HCP and HCO profiles, and starting an email or SMS from a contact. One flow checks that masked values can't be contacted.
  • Latency in the request path. Timers at the DAO and resolver layers log per-request search time to CloudWatch from day one.

05 · Planning

Ship in thin, safe slices

Risk · blocking the UI
Requirement
  • Frontend work starts at the same time as the backend (R6)
  • Reviews need to stay small on a regulated codebase
How I'd solve it

Build order keeps every step mergeable: data access with tests, then the API, then paging, permissions, masking, and profiles. Each layer lands before the UI needs it. Large items split into "Part 1 / Part 2" PRs so reviews stay small, and every change is additive, so nothing needs a revert.

Order: DAO → API → paging → access guard → masking → profile → relations → ranking + load test

Risks

What could go wrong, and how the design handles it

Multi-tenant, regulated platform

Risk

Per-customer Postgres schemas and HIPAA access tiers make it easy to query the wrong tenant or show the wrong field.

Mitigation

Resolve the tenant from the request context once, and test masking and access as part of the API contract.

Six data shapes, one result list

Risk

Relational rows, JSONB documents, and nested arrays have to rank and page together.

Mitigation

Per-entity CTEs that emit one common row shape, with a composite key for caregivers who have no ID.

Permissions before data

Risk

Filtering after the query would leak counts and break paging.

Mitigation

The access guard decides allowed types and links first, and the SQL is built only from what is allowed.

Masking that stays consistent

Risk

Mask strings defined twice, collisions with real data, and sort order based on hidden values.

Mitigation

Masking in SQL, shared sentinel constants, and masked values sorted as empty with an external-ID fallback.

A contract under active use

Risk

Two frontend engineers build on the API while it is still changing.

Mitigation

Additive changes, staged deprecations, the shared Page interface, and pairing with the UI engineers on the profile endpoint.

Free-text input into SQL

Risk

Search text feeds Postgres regex matching, so special characters could break queries.

Mitigation

Parameterized queries, escaping of Postgres and regex reserved characters, trimming, and plain-language errors the UI can show reps.
